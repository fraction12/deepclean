# Core Concepts

## Report-first cleanup

Deepclean is a local analysis and planning system, not an autonomous repo-wide rewrite tool. It helps humans and agents decide what to inspect next, why it matters, and how to verify a bounded change.

The default path is read-only: inspect state, scan, read the queue, generate a plan or handoff, then decide whether one guarded local fix is appropriate.

## State directory

Deepclean writes durable local artifacts under `.deepclean/`:

- `runs/` stores scan metadata.
- `features/` stores semantic feature and work-unit maps.
- `evidence/` stores local evidence records.
- `synthesis/` stores provider attempt ledgers and candidate validation results.
- `findings/` stores stable finding records.
- `observations/` stores run-specific observations linked to stable findings.
- `candidates/` stores cleanup candidates.
- `clusters/` stores related cleanup themes.
- `opportunities/` stores campaign opportunities.
- `reports/` stores Markdown and JSON reports.
- `plans/` stores focused implementation plans.
- `handoffs/` stores agent-ready task packets.
- `triage/` stores local triage notes.
- `lifecycle/` and `revalidations/` store finding history and freshness checks.
- `ci/` stores CI policy runs.
- `locks/` stores writer-lock records.
- `retention/` stores prune manifests.
- `fixes/` stores guarded fix attempt ledgers and verification evidence.

Add `.deepclean/` to `.gitignore` unless the repository deliberately shares generated reports.

## Candidates and themes

Findings are stable issue records. Candidates are run-specific cleanup observations tied to findings. Themes group related candidates into a larger cleanup area.

Broad themes can be marked `too-broad` when they should not be handed to an agent as one task.

## Campaign opportunities

`deepclean campaign` turns current findings and candidates into PR-sized opportunities. Opportunities carry slop type, fixability, priority, evidence, target candidates/findings, verification, and a suggested next step.

Fixability controls execution:

- `auto-fixable` targets may enter guarded fix/work execution.
- `safe-agent` targets should produce a plan or handoff for a bounded agent repair.
- `design-needed` targets need a design/spec decision first.
- `blocked` and `stop-campaign` targets should not be pushed into source mutation.

## Privacy modes

Local evidence is collected before provider-backed synthesis. Source samples are redacted from synthesis prompts by default. Use `--evidence-only`, `--offline`, or `--local-only` when provider execution is not allowed.

Use `--allow-source-in-model` only when the target repository and provider configuration are allowed to receive source excerpts.

## Guarded fixes

Deepclean recommendations are not automatic fixes. Guarded source mutation requires a single auto-fixable target, explicit apply flags, proof inputs, and verification commands.

```bash
deepclean fix candidate-001 --mode guarded --patch ./fix.patch --dry-run --json
deepclean fix candidate-001 --mode guarded --patch ./fix.patch --apply --verification "npm test"
deepclean work candidate-001 --mode guarded --branch chore/deepclean-fix --apply --verification "npm test" --pr
```
